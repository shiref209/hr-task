# Spec: API Docs — OpenAPI / Swagger

Status: **approved 2026-10-09**. Depends on: `api-foundation`, `employees`.

## Objective
Every endpoint is documented in OpenAPI 3, browsable in Swagger UI, and exportable as a file reviewers can import into Postman/Insomnia — without writing any schema twice.

## Decisions
- `@nestjs/swagger` (approved). Swagger UI at `/docs`, raw document at `/docs-json`.
- Schemas are **generated from the shared Zod schemas** with Zod 4's built-in `z.toJSONSchema()`; no `@ApiProperty` DTO classes.
- Success responses are documented wrapped in the envelope (`{ data, meta? }`); error responses as `ProblemDetails` with `application/problem+json`.
- Enabled unless `SWAGGER_ENABLED=false` (env, validated in `appConfig`, default `true`; set `false` in production).
- `pnpm --filter api docs:export` writes `docs/openapi.json` (repo root) **without a database or HTTP server**; the file is committed.

## Implementation contract
- `apps/api/src/docs/`
  - `openapi.ts` → `buildOpenApiDocument(app: INestApplication): OpenAPIObject` (title "HR Payroll API", version from package.json) and `setupSwagger(app, { enabled }: { enabled: boolean })` (mounts `/docs` + `/docs-json` only when enabled; `main.ts` passes `appConfig.SWAGGER_ENABLED`).
  - `zod-openapi.ts` → small helpers turning a Zod schema into decorator options: `apiBody(schema)`, `apiEnvelope(schema, { paginated? })`, `apiProblems(...statuses)`, `apiQuery(schema)`. Input schemas use `z.toJSONSchema(schema, { io: 'input' })`, responses `{ io: 'output' }`.
  - `export-openapi.ts` → script entry: builds the app with repository/storage tokens overridden by no-op stubs (no DB connect), writes `docs/openapi.json` (pretty-printed, stable key order), exits.
- Schemas whose rules depend on "today" are documented via `buildCreateEmployeeSchema({ today: 'YYYY-MM-DD' })` with a description noting hire date must not be after today in `APP_TIMEZONE`.
- The shared error shape gets a Zod source of truth: `errorDetailsSchema` in `types/src/common/problem-details.ts` (the `ProblemDetails` type becomes `z.infer` of it) so the docs component is generated, not hand-written.
- Controllers gain only decorators (`@ApiTags`, the helpers above); no logic changes.

## Edge cases
1. Every registered route (departments + employees, incl. restore and profile-image) appears in `paths` with its method — a test compares the router's routes to the document, so a new endpoint without docs fails CI.
2. `POST /employees` body schema: required fields listed, `additionalProperties: false` (strict), `baseSalary` a string with its pattern, enums for `status`/`type`.
3. Each endpoint documents its real error statuses (e.g. POST employees: 400, 409; PATCH: 400, 404, 409, 422) referencing one shared `ProblemDetails` component, content type `application/problem+json`.
4. List endpoint documents query params from `employeeListQuerySchema` (page/pageSize bounds, enums, `deleted`) and the paginated envelope with `meta`.
5. Profile-image upload documented as `multipart/form-data` with a binary `file` field, max 2 MB and allowed types in the description.
6. `SWAGGER_ENABLED=false` → `/docs` and `/docs-json` return 404 (as Problem Details).
7. `docs:export` runs with no `DATABASE_URL` reachable and produces byte-identical output on repeated runs.

## Testing strategy
- e2e (in-memory fakes, like `employees.e2e-spec.ts`): fetch `/docs-json` and assert cases 1–6.
- Export: a unit test calls `buildOpenApiDocument` on the test app and asserts determinism (two builds deep-equal); the script itself is smoke-run once.

## Success criteria
Swagger UI shows every endpoint with request/response/error schemas; `docs/openapi.json` is committed and regenerated by one command.
